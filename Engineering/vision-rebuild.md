# 识别系统重构方案（号码识别）

> 这份文档是重构的**唯一事实来源**。所有像素测量都来自真实票面照片，
> 不是估计值。开工前先完整读一遍。

## 一、要解决什么

**标签信息（彩种、期号、开奖日期、倍数、合计）目前识别已经够用，不动它。**
问题**全部**集中在号码球：

| 症状 | 真机实例 |
|---|---|
| 整排错位 | 七星彩每注前面凭空多个 `0`，特别号整列消失 |
| 两位数丢十位 | 特别号 `13` 读成 `3`、`10` 读成 `0` |
| 无关数字被当成号码 | 排列5 把票底流水号 `00084` 读成唯一一注 |
| 裁切稍微不准就整张认不出 | 排列3 |

最危险的不是"认不出"，是**认错了还看起来对** —— `00084` 和 `3` 都是合法号码，
用户不拿票面逐位比对根本发现不了。

## 二、根因

当前流水线在**用户裁切之后直接做 OCR**，中间缺了「配准」这一步。
所有几何判据（列距、行距、边界）都只能**从识别结果里估**，
而裁切框本身是歪的、松的，估出来的东西自然跟着偏。

真正的锚点应该来自**票面自己印上去的东西**，而不是用户的裁切框。

## 三、实测数据（重要，不要重新猜）

### 3.1 体彩数字型：上下两条虚线就是基准

七星彩、排列5、排列3 的号码区被**两条长虚线**夹住，中间还包含

检测判据（三张票实测，**零误报**）：

段数 ≥ 12

占空比 0.25–0.75

|---|---|---|
| 七星彩 | 24 | **2** |
| 排列5 | 18 | **2**（其中一条仅 1 像素高也抓到） |
| 排列3 | 9 | **2** |

## 四、新架构

```
                     ┌─ 体彩：虚线检测（自己算）
粗裁切 → 基准检测 ───┤
   │                 └─ 福彩：哈希行 + 开奖期行（Vision 给四边形）
   │                        ↓
   │                  TicketFrame { 号码区四角, 左边界, 右边界 }
   │                        ↓
   │                  单应配准 → 号码区摆成标准矩形
   │                        ↓
   │                  网格（列距行距成常数，不再估）
   │                        ↓
   │                  逐格识别 → 认不出标问号
   │
   └─ 标签路（整票中文 OCR）→ 彩种/期号/日期/倍数/合计   ← 完全不动
```

配准之后这些麻烦一次性消失：列距行距变常数、注序号列和倍数列在标准矩形里
是固定位置、七星彩那 1.58 个列距变成画好的格子、裁松裁歪不再有影响。

**号码区需要左右两个边界**：
- 左 = 注序号 / 玩法标签列的右侧（`①②③④⑤` / `A.B.C.` / `组六:`）
- 右 = 倍数列 `(N)` 的左侧 ← **当前代码缺这个，见下面已知 bug**

## 六、硬约束（不可违反）

1. **每一个号码都必须能说出它来自票面的哪个像素格子。**
   说得出来的才允许导入，说不出来的标问号（`NumberSet.unknown`）。
   问号未补齐**禁止导入票夹**。这样"看起来正常的错误结果"在结构上不可能出现。
2. **摆不上栅格宁可整个矩阵作废、退回上一层**，绝不允许错位。
   少认一注可以接受（用户看得见），错位不可以（用户看不见）。
3. **号码路和标签路彻底分开**，标签路一行都不要动。
4. **隐私**：全部识别在本机完成，照片不上传、不写入数据库。
   **不得引入任何云端 OCR** —— 会推翻已提交 App Store 的审核备注和隐私政策。
   端上第三方 OCR（Tesseract/PaddleOCR）也不要：它们同样按「先找文本行」工作，
   在矩阵排版上会犯一模一样的错。
5. 各彩种的配色方向不变；号码球数字保持白色。

## 七、已知的具体 bug（重构时必须一并解决）

1. **福彩 3D 的矩阵路径从来没跑起来过**：行尾 `(1)` 里的 `1` 被 tokenize 当成
   第 4 个号码，`isBetRow(columns: 3)` 因为 4 > 3 直接拒掉。号码区缺右边界。
2. **七星彩两位数特别号丢十位**（`13`→`3`、`10`→`0`），build 32/33/34 三次尝试都没修好。
3. `VNRecognizedText.boundingBox(for:)` 在 `.accurate` 下对同一个词里的**每个字符
   返回同一个框**（Apple 技术支持确认的 bug）。要逐字符坐标**必须用 `.fast`**。
4. `①` 在 Unicode 里是有数值的数字字符（`wholeNumberValue == 1`）。
   按坐标取字符时必须用 `TicketTextParser.plainDigitValue`，不能用 `digitValue`。
5. 数字型彩种值域是 0-9，**任何数字字符都是合法号码** —— 票底流水号 `00084`
   曾被读成一注。现在靠「号码必须按空白隔开」挡住，重构后要保留等价的保护。

做完的东西：

**阶段 1 一行识别代码都没改。** 配准跑在识别之后，只读不写 ——
先让「摆正没摆正」肉眼可判，再把识别接上去（阶段 2）。
反过来做的话，结果一旦不对，没人分得清是配准错了还是识别错了。

### 唯一一处补充实测的地方：投影方向要跟着票斜

判据里「高 ≤ 6 行」是个**像素数**，它只在量它的那个分辨率、
而且票**摆得正**的时候成立。两件事因此定下来：

1. 所有像素判据都在固定的工作宽度 **1000px** 上说话（`InkMask.workingWidth`）。
   直接拿 4400px 的正片去套，同一条虚线会变成二十几行高。
2. 横向投影沿票面自己的倾角做，不是沿图像的行。
   合成票实测：一条横跨 950px 的虚线歪 **0.46°**，按行投影量出来就是 **高 8** ——
   判据当场失效，两条线一条都找不到；沿 0.29° 投影再量，
   两条都回来了，而且重心拟合把真实倾角 0.008 还原到了 0.00806。

   预处理那一步只在认出至少三块文字时才拉平基线，拉不动的票就是这个样子。

   `slope == 0` 时两种投影**完全等价** —— 第三节那张表里的数一个都没动。
   `measure.py` 同步加了同一套扫倾角的逻辑，两边要一起改。

## 十一、第一轮真机反馈（build 35 → 36）

真机表现：裁切框**不动**、直接用自动框出来的那个，三张体彩票的绿线蓝框粉格
都对得上，配准后的号码区排得整整齐齐。但是**只要把框拖歪一点、拖松一点，
就一条线一个框都没有**。

### 量出来的根因：判据拿整张照片当分母

合成票实测（票 800×520，四周填深色/浅色桌面）：

| 情况 | 大津阈值 | 虚线横跨 | 命中 |
|---|---|---|---|
| 裁得紧（票≈整幅） | 79 | 0.97 | **2** |
| 四周各留 60px + 深色桌面 | 101 | —— | **0**（连候选细带都没有） |
| 四周各留 160px + 深色桌面 | 104 | —— | **0** |
| 四周各留 160px + 浅色桌面 | 79 | **0.69** | **0**（判据要 > 0.80） |
| 同上，**只量票面那一块** | 79 | 0.97 | **2** |

两种失效模式叠在一起：

1. **大津法被桌面带偏。** 裁进来一圈深色桌面，阈值从 79 跳到 104，
   整片桌面被当成"墨"，行投影全饱和，虚线连候选横带都切不出来。
2. **横跨判据误伤。** 同一条虚线，分母从票宽换成照片宽，横跨就从 0.97 掉到 0.69。

修法**不是放宽判据**（那会把票号行之类的东西放进来），而是
**只量票面那一块**：`InkMask.make(_:region:)` 先按票面裁一刀，
`region` 取识别到的文字的包络往外让 3%。让完之后，裁松裁歪量出来的数
和裁得严丝合缝时**一模一样**。

这跟 `rowLabelBoundary` 当年那条注释是同一个病：**判据要相对票面算，
不能相对整张照片**。

### 顺带修掉的两处

- **票歪多少改成量出来的。** `VNRecognizedTextObservation` 给的是四边形，
  文字行自己的走向就是票面倾角（`TicketVisionScanner.textTilt`），
  投影方向直接从它开始试，不用从 0 挨个扫。扫一圈仍然留着兜底。
- **虚线取内沿，不取中线。** 实测大乐透第③注的格子整行消失：
  最后一注和下面那条虚线在投影上连成一条带，一行切出几十段被判掉。
  号码区是夹在两条线**中间**那一块，边界本来就该是内沿。
  顺带让绿色基准线从蓝框底下露了出来。

### 五张真票复核（26051/26042 七星彩、26088 排列5、26088 排列3、26102 大乐透）

拿**原始照片**（没经过 App 的透视矫正，比 App 看到的更难）量：

| | 整张照片 | 只量票面那一块 |
|---|---|---|
| 七星彩 26051 | 0 | **2** |
| 七星彩 26042 | 0 | **2**（要沿 −0.29° 投影才量得出来）|
| 排列5 26088 | 0 | **2** |
| 排列3 26088 | 0 | **2** |
| 大乐透 26102 | 0 | 0 |

**0/5 → 4/5。** 七星彩 26042 正好验证了倾角那条：按图像的行投影找不到。

大乐透那张是票斜躺在桌上拍的，轴对齐裁切之后虚线摊到 8 行高，超过「高 ≤ 6」。
App 在这一步之前有透视矫正兜着（build 35 在同一张票上是找到框的），
所以这张照片不代表 App 看到的东西 —— 但它说明：**透视矫正要是没做好，这一层会塌。**

### 工作宽度 1000 是上限，不是起点

把票面分别缩放到 300/360/420/500/600/800/1000/1200 px 宽各量一遍：

- **300 → 1000 px 全都稳**（四张票都是 2 条）
- **1200 px 反而掉**：两张七星彩都从 2 条掉到 1 条

插值放大会把虚线插胖、把相邻的段黏起来，段数掉到 12 以下。
所以 `InkMask.workingWidth = 1000` **不要往上调** ——
"提高分辨率应该更准"在这里是反的。

### 加的东西：票头区

用户要求把重要字段都框出来，不只框号码。体彩现在多画一个框：
以号码区上边界那条虚线为底，往上罩到「第 N 期 / 开奖日期」那一行
（中间那行机号一起罩进去）。底边和号码区共用同一条基准，两块严丝合缝。

**只标不读** —— 标签路按硬约束三一行不动。

福彩的票头区（哈希行上方的「玩法 / 机号」那一行）要等阶段 3 的哈希行基准，
到时候和号码区基准一起上。

### 还没做、留给后面阶段的

- 号码区右边界现在只认「整块就是 `(N)`」的碎片。福彩 3D 那条
  `组六: 1 8 9 (1)` 被 Vision 连成一整块时仍然取不到 —— 阶段 3 用四边形基准解决。
- 调试图里的"格子"是**墨迹自己划出来的**（行投影 × 列投影），
  还不是按版式吸附过的栅格。把它们吸附成规整的栅格、补空列、逐格识别是阶段 2。

## 十二、阶段 2 第一轮真机反馈（build 39 → 40）

三张票，三个毛病，根子各不相同。

### 1. 七星彩特别号还是丢十位（`13`→`3`、`10`→`0`）

**列位取中位数取错了。** 特别号那一列是**右对齐**的：`13` 的十位往左探出去，
`4` `9` `2` 不探。五注里三注是一位数，中位数就落在个位那一段上 ——
十位的 `1` 落在列外面，`bucket` 直接把它丢掉。

修法：**这一列取并集，不取中位数**。只要有一行印了两位，这一列就得容得下两位。

顺带补了一步「相邻两段合并」：实测号码之间空 55px，而 `13` 里的 `1` 和 `3`
只空 14px、字宽 21px ——「间隙小于一个字宽就是同一个号码」。不合的话
两位数的特别号会占掉两段、和别的行对不齐，那一注整个被判掉。

### 2. 福彩 3D 只读出两注 / 排列3 少一注

两张票都是**多切出来一列**，`segments.count <= columns` 一刀把整行判掉，
于是退回老路。多出来的那一列是两样东西：

| | 多出来的是 | 怎么分开 |
|---|---|---|
| 左边 | 注序号 `①②③` / 玩法标签 `组六:` | 实测列距 62.5 对 65，**几何上分不开** → 靠内容：这一列里一个数字字符都没有（`①` 是带圈的，`plainDigitValue` 不认它） |
| 右边 | 倍数 `(N)` | 实测离号码 **2.7 个列距**，而七星彩的特别号（离得最远的号码）才 **1.58** → 拿 **1.8** 当界一刀切，两边余量都够 |

这就是「福彩 3D 的矩阵路径从来没跑起来过」那个老 bug 的真正解 ——
以前靠 Vision 认出独立的 `(1)` 碎片来定右边界，而 Vision 经常把它
连进号码行（真机原文里是 `组三：0 9 (`）。现在右边界是**量出来的**，不靠 OCR。

`fits` 跟着放宽：落在号码区**外面**的段（注序号、倍数）不算数，
但落在里面却不在任何一列上的，说明这行不是投注行。

可**票面上印的是 `4`**，只有到 10 以上才印两位。核对彩票这件事，
屏幕和票面不一致就是错的。

`GameSection.padsNumbers` 统一这条规则（`range.upperBound > 9 && key != .tail`），
号码球、票夹卡片、开奖号码、导出文本六处调用全部走它。

### 1. 七星彩：裁列的判据撞在自己文档记的坑上

上一轮用「这一列里一个数字字符都没有就是注序号列」来裁掉 `①` 那一列。
可第七节自己就记着：**`.fast` 会把圈码 `①` 读成 `0`** —— 注序号列里于是
"有数字"，判据失效，8 列裁不到 7 列，整个矩阵作废。

真机上五行各切出 8 段、格子位置全对，就死在这一步。修法是换成
**完全不依赖 OCR 的几何判据**：号码是等距等宽印的，从多切出来的那些列里
挑出最像号码矩阵的**连续一段**，打两项分（都无量纲，跟裁切和拍摄距离无关）：

| 打的分 | 怎么算 | 为什么 |
|---|---|---|
| 列距 | 末段列距先除掉 `trailingPitch` 折算成标准列距，再取偏中位数最远的那一段 | 有**一段**列距不对，这段窗口就是错的 → 取 max |
| 字宽 | 各列宽偏离中位宽的**平均值** | 某一列碰巧全是 `1`（笔画细）不该一票否决掉正确的窗口 → 取平均 |

`score = 列距偏差 + 0.7 × 字宽偏差`，分最低的那一段就是号码。

权重 0.7 是拿四种版式的实测列位扫出来的，不是拍的：

| | 只看列距 | 列距 + 0.7×字宽 |
|---|---|---|
| 七星彩（①+6+特别号） | 对 | 对 |
| 排列5（①+5） | ±3px 抖动下 411/500 | **500/500** |
| 排列3（①+3） | ±3px 抖动下 361/500 | **499/500** |
| 福彩 3D（标签+3+倍数） | 对 | 对 |

排列3 是最难的那一个：注序号列距 62.5 对号码列距 65，只差 4%，
光看列距分不开（第 3.2 节早就记着「几何上分不开」）。字宽那一项才是决定性的 ——
`①` 带个圈，比数字宽 30%。

数字字符只留作一道**否决**：挑中的这一段里至少一半的列得有数字，
否则是整段压在中文标签上了。这一条不依赖 `①` 读成什么。

顺带把 `1.8 个列距一刀切` 那条也去掉了 —— 倍数列 `(1)` 的列距（2.7）和
字宽（35px，数字的两倍多）两项都对不上，`window` 自然挑不中它，不用再设界。

### 2. 福彩 3D：段数上限把整张票判掉了

`候选行 0 条` 不是没切出行，是切出来的行**全被段数上限筛掉了**。
上限当时是 `columns + 2` = 5，而中文玩法标签会被切成好几段
（`组` 是 纟 + 且），实测每行切出 **11 段** —— 和第十节记的
「配准后切出 5 行、54 格」（54 ÷ 5 = 10.8）完全对得上。

上限放宽到 `columns + 8`。该留哪几列交给 `window` 按版式挑，不在这一步瞎砍。

调试图也跟着补一条：划不出格子时，把**没过筛子的原始段数**也报出来
（`墨迹带 7/7/7/7/7 段`）。否则「候选行 0 条」看不出是压根没切出带来、
还是段数卡在上限外面 —— 这一轮就为了这一个区别多花了一次真机往返。

### 2. 阶段 4：大乐透实测

拿 26102 那张真票量的（照片歪 3.6°，先摆正再量）：

```
① 12 15 19 31 33  +  05 09
```

| 内容 | x 范围 | 宽 |
|---|---|---|
| `①` | 39–58 | 20 |

| 后区 2 个号码 | 345–370 / 388–415 | 27 |

- 一行没有倍数列，倍数印在票头（`追加投注3期2倍`）

### 3. 「分组」把两件事变成了同一件事

大乐透这张票逼出来两个老架构做不到的东西：

1. 号码矩阵**中间夹着一段不是号码的墨**（`+`）
2. 一格印**两位数**

第一件事顺手解决了七星彩那个特例。原来的 `window` 是「挑一段**连续**的列」，
七星彩的特别号靠一个专门的 `trailingPitch` 补丁往后够；大乐透的 `+` 一夹进来，
连续窗口无论怎么挑都挑不对（实测最好的那个窗口得分 0.318，还是错的）。

改成 `DigitTicketLayout.groups` 之后，两件事是同一条规则：

| | 分组 | 组间距 | 中间印分隔符 |
|---|---|---|---|
| 排列3 / 福彩3D | [3] | — | — |
| 排列5 | [5] | — | — |
| 七星彩 | [6, 1] | 1.58 列距 | 否 |
| 大乐透 | [5, 2] | 2.34 列距 | **是**（`+`） |
| 双色球 | [6, 1] | **待实测** | 是（`-`） |

挑列的规则变成「**每一组挑一段连续的，组与组之间可以跳过几段**」——
跳过的那几段就是分隔符。打分还是列距 + 字宽两项，只是列距先按
`groups` 给的倍数折算。实测大乐透那张票：正确的挑法得分 **0.026**，
第二名 0.318，差了 12 倍。

`fits` 跟着放宽：落在**组与组之间那段空当**里的墨不算数（`+` 就在那儿），
落在别处却不在列上的，依然说明这行不是投注行。不放宽的话每一条投注行
都会被判掉，一注都读不出来。

### 4. 合并阈值从 1.0 个字宽收到 0.75

两位数的两个数字要合成一段，号码与号码之间不能合。把实测间隙都按
÷ 字宽 折算之后，两侧最紧的是：

| 该合 | | 不该合 | |
|---|---|---|---|
| 七星彩 `13` 里的两位 | 14 ÷ 21 = **0.67** | 大乐透 `①` → 第一个号码 | 11 ÷ 13 = **0.85** |
| 大乐透 `12` 里的两位 | 3 ÷ 13 = 0.23 | 双色球 号码之间 | 15 ÷ 18 = **0.83** |

取几何中点 **0.75**，两头各留 12%。老的 1.0 会把大乐透的注序号粘到第一个
号码上，双色球更会整行合成一段。

### 5. 两区票现在也能带问号

大乐透和双色球以前只有「整行读成一注」和「整行丢掉」两种结果 ——
少认一位，三注的票在票夹里就变成两注，而且看不出少在哪儿。
现在 `singleLine` 先按位置读（`positionalValues`），认不出的那一格
带着问号上复核页，和数字型彩种一样。判据很紧：要求正好切出这么多段、
每段最多两位，所以票面原文里带 `+` 的行、OCR 把两个号码并成 `0512` 的行
都过不去，照旧走按分隔符 / 按个数拆的老逻辑。

### 6. 还没做的两件事（都需要真票）

- **双色球没切过去。** 文档里只记着列距 51、两位数宽 36、`(3)` 距最后一个
  号码 0.43 个列距 —— 红蓝之间隔几个列距**没量过**。按项目约定
  「拿到新票照片先量一遍再动代码」，没量之前不写它的 `groups`。
  而且它的号码之间只空 0.83 个字宽，是所有票里最挤的，合并阈值那一侧
  只剩 12% 余量，必须拿真票复核。
- **老路还留着。** 阶段 4 要求「旧的文本解析路删除，不留两套并行实现」，
  但七星彩、福彩 3D、大乐透三条新路一次真机都还没跑过。先留着兜底，
  等这一轮真机确认三种票都走格子路之后再删 —— 硬约束二说的是"宁可整个
  矩阵作废、退回上一层"，上一层现在还得有东西。

  只有一格一位的那几种票能退到 `DigitMatrixReader`：它是按「一列一个个位数」
  写的，大乐透喂给它只会读出垃圾，所以两位数的票配准失败直接退到逐行二次识别
  （`DigitTicketLayout.singleDigit`）。

### 7. 差点漏掉的一个静默错误：票头被当成了号码区

量大乐透那张票的时候顺手扫了一遍所有倾角，发现一件事：

```
 -3.72°  真虚线    相距 158 (27% 票高)   ← 正确
 +2.00°  期号行 + 哈希行  相距 48 (8% 票高)  ← 五条判据全过
```

照片歪 **3.6°**，超出了兜底扫描的 ±2°，真虚线一个倾角都量不出来；
而沿 +2.0° 投影时，票头的 `第26102期` 行和哈希行 `110310-292261-…`
被**摊成了两条 5 格高的窄带** —— 一行数字加短横，本来就长得像虚线，
「高≤6 / 横跨>80% / 段数≥12 / 最长段≤5% / 占空 0.25–0.75」五条全过。

按 App 真实的扫描顺序模拟，大乐透会锁在这一对上，号码区被框到票头上，
**而且看起来一切正常**。硬约束二针对的正是这种错。

（主路不会走到这儿：`slopes(around:)` 先试文字量出来的倾角，−3.6° 那档
直接命中真虚线。出问题的是文字倾角量不出来时的兜底那一圈。）

**试过但没走通的判据**：集中度（带内墨量 ÷ 带外一个字高内的墨量）。
直觉上真虚线是孤立的窄尖峰、被摊开的文字行则墨都在旁边，但实测：

| | 集中度 |
|---|---|
| 大乐透真虚线 | 0.72 / 0.83 |
| 大乐透假线对 | 0.16 / 0.21 |
| **七星彩 26051 真虚线（上）** | **0.36** ← 它下面紧挨着合计行 |
| **排列5 26088 假线对** | **0.45 / 0.41** |

真的比假的还低，分不开。**这条记下来，别再试第二遍。**

**走通的判据**：两条线之间得装得下一个号码区。

| | 相距 ÷ 票高 |
|---|---|
| 七星彩 26051 真 / 排列5 26088 真 / 大乐透 26102 真 | 26% / 29% / 27% |
| 排列5 26088 沿 −1.15° 的假线对 | **4%** |
| 大乐透 26102 沿 +2.0° 的假线对 | **8%** |

取 8% 和 25% 的几何中点 **15%**，两头各留 1.7 倍。按 App 的扫描顺序复跑：
七星彩和排列5 命中的倾角和结果一个字没变，大乐透从"锁在假线对上"
变成"一条都没凑出" → 退回文字行基准，也就是用户真机上已经验过的那条路。

兜底那一份（调试图用的）也跟着过这道闸：正好两条、中间却装不下号码区的
不能留，否则 `TicketFrame.between(rules:)` 照样拿它去配准，等于没挡。

## 十五、build 43 真机结果

三张票三个不同的结论，外加第一张双色球真票。

| 票 | 结果 |
|---|---|
| 福彩 3D | **五注全对，走格子路** —— 阶段 3 达标 |
| 七星彩 26042 | 走了格子路（35 格认出 35 格），但**特别号还是丢十位**（`13`→`3`、`10`→`0`）|
| 大乐透 26102 | 号码对，但**没走格子路** |

### 1. 七星彩：格子画对了，是「补认」没轮到它

调试图上末列那个框明明白白框住了两位（`wideningTail` 生效了），
可读出来还是 `3`。根因不在几何，在补认的**触发条件**：

```
整块认一遍 → 这一格拿到 `3`（十位那一竖又细又淡，整块图里 Vision 直接漏了）
→ 补认只跑「空格子」→ 这一格有值，永远轮不到它
```

`reread` 会把一格单独裁出来放大 10/16 倍再加一遍对比度，十位就出来了 ——
七星彩的 `13` 一直读成 `3`，卡的就是这一步。

修法：**印得下两位、却只读出一位的格子也要补认**，而且只在补认真的读出
两位时才换（读回同一个一位数就别动）。每张票最多 5 格，不贵。
大乐透的 `05` 本来就读出两位，不会进来。

### 2. 大乐透：几何全对，栽在那道「数字否决」

调试图报的是：

```
墨迹带 4/9/9/9 段，候选行 3 条，对得齐 3 条，每行切出 9/9/9 段
```

—— 段数、候选行、对齐**全对**（9 = ① + 5 个前区 + `+` + 2 个后区）。
把调试图里那张「配准后的号码区」抠出来缩回 1000 宽复跑一遍：

```
列位 9 段，各挑法得分：
  [0,1,2,3,4,5,6] 0.660      [0,1,2,3,4,6,7] 0.318
  [1,2,3,4,5,6,7] 0.603      [1,2,3,4,5,7,8] 0.082  ← 正确
三行全部 fits=True
```

几何算得清清楚楚，差了四倍。唯一能让它整个作废的就是那道
**「挑中的列里不到一半有数字就作废」**的否决 —— 而它依赖 Vision 的字符坐标。

把 `digitCenters` 清空复跑：**七星彩、福彩 3D、大乐透三种版式照样全挑对。**
组结构 + 列距 + 字宽三项已经足够，OCR 这个弱信号不该有一票否决权
（何况 `.fast` 还会把 `①` 读成 `0`）。所以改成**扣分**，不再作废。

调试图也补两项：定出几列、挑列成没成、Vision 认出几个数字字符 ——
这一轮就是因为报不到这两步，只能靠抠截图反推。
另外「老路也没读出来」那句话是错的：两位数的票根本不走老路，现在照实说。

### 3. 双色球：**不切到格子路**，它根本不是矩阵排版

第一张双色球真票（2026081 期）实测：

```
A.01 04 14 23 27 32-12  (3)
B.01 03 12 19 25 26-10  (3)
C.04 12 25 26 27 30-03  (3)
D.-- -- -- -- -- -----  (-)
E.-- -- -- -- -- -----  (-)
```

一行的原始列段（C 行，字宽 15–16）：

| 内容 | x | 和左邻的间隙 | ÷字宽 |
|---|---|---|---|
| `C` `.` `0` `4` | 13–28 / 36–40 / 47–62 / 65–79 | 8 / 7 / 3 | 0.5 / 0.45 / 0.2 |
| `12` `25` `26` `27` | … | 19–21 | **1.3** |
| `30` **`-`** `03` | 301–333 / **335–350** / 352–384 | **2 / 2** | **0.13** |
| `(3)` | 406–450 | 22 | 1.4 |

**分隔符 `-` 和两边的号码只隔 2px（0.13 个字宽）**，比号码自己两位之间还紧。
墨迹投影无论怎么切都会把 `30-03` 连成一段，`C.` 也会粘到第一个号码上。
合并之后一行是 7 段，正好等于 7 个号码 —— **段数对得上，内容全错**，
而且看起来一切正常。这是最坏的一种失败。

对比大乐透：`+` 独立成段（宽 10px，两边空 32/35px），号码之间 1.36 个字宽。
两家打票机的排版根本不是一回事。

顺带纠正文档 3.3 节旁边记的那行：这张票实测**列距 51**（对得上），
但号码之间的间隙是 20px、字宽 15.5px，比值 **1.29** 而不是 0.83 ——
之前那个数应该是拿两位数整体宽度 36 减出来的，不是真实间隙。
`merging` 的 0.75 阈值在这张票上余量很足。

**结论：双色球留在文本路。** 矩阵架构解决的是「Vision 按竖列读」那个问题，
而双色球的一行是一团紧凑字符，Vision 从来都读得对（文档第二节自己写着）。
给它上格子路是拿一个它没有的病去治它，还会引入上面那种静默错误。

阶段 4 因此收敛成：**大乐透切到新架构，双色球明确不切**，理由是实测排版。

## 十六、build 44 真机 + 一条架构界线

### 1. 七星彩：问题在**补认那一格**，不在几何

调试图：`号码按配准后的格子读：5 注 × 7 位，35 格里认出 32 格`，
末列画的框在调试图上明明白白框住了 `13` `4` `9` `10` `2` 两位都在里面。
可五注里三注是问号，一注读成 `0`（真值 10），只有 `2` 对。

注意真值：第 2、3 注的特别号是 **`4`** 和 **`9`**，本来就是一位数 ——
连一位数都读不出来，说明毛病不在"两位数读不全"，在**补认这一步整个失手**。

根因在 `reread` 的这一行：

```swift
guard (1...2).contains(chars.count) else { continue }
```

裁的时候左右各让了 0.8 个格宽（Vision 贴着字边裁经常什么都不给），
邻居的一位数很容易跟着进来 —— 一旦认出 3 个字符，**整遍结果直接丢掉**，
这一格就成了问号。上一版还以为是"认不全"，其实是"认全了反而被丢"。

修法：认出来的字符按**格子自己的范围**再筛一道，落在格外的是邻居，
筛完再判 1–2 位。格子在哪儿是墨迹量出来的、可信；认出几个字符是 OCR 说的、
不可信 —— 拿可信的去筛不可信的，而不是一票作废。
放大倍数也从 10/16 改成 8/12/18，多给两档。

调试图补一句：`整块认一遍剩 N 格空的，补认补上 M 格`，
下一轮直接看得出补认到底有没有在干活。

### 2. 大乐透：`select` 通了，卡在收行

`定出 9 列，挑列挑中 7 列，Vision 认出 48 个数字` —— 上一轮改的那两处都生效了：
否决改成扣分之后挑列成功，7 列挑对。但仍然"划不齐"，说明剩下的唯一一步
`fits` 把三行全判掉了。

按调试图抠出来的列位复算：注序号中心 38，最左那列下沿 88，
容差 = 中位列宽 68 × 0.6 = 40.8 → 判"在格外"的门槛是 47.2。
**38 对 47.2，只差 9px**（在 1000 宽的图上）。手工抠图的误差就不止 9px，
真机上稍微偏一点，注序号就会被判进第一列，第一个号码跟着抢同一列，
`fits` 返回 false，三行全没。

要修的话得把 `fits` 的绑定改成"每一列挑最近的那一段"而不是"第一个落在容差里的"。
**但这一轮先不动** —— 见下面那条界线。

### 3. 界线：**哪些彩种需要格子，哪些不需要**

用户问得对：双色球、大乐透、七乐彩、快乐8 这些两位数的票，是不是根本不用格子，
把基准和号码区框准就够了？

是。而且有一条能写成规则的界线 —— **号码本身是不是自带校验**：

| | 号码取值 | 自带校验 | 结论 |
|---|---|---|---|
| 排列3/5、七星彩、福彩3D | **0–9，任意数字都合法**，可重复、无顺序 | **没有** | **必须走格子** |
| 双色球、大乐透、七乐彩、快乐8 | 两位数，**升序、不重复、有值域** | **有** | 不需要格子 |

第七节第 5 条早就记着这件事的另一半：数字型彩种「票底流水号 `00084` 曾被读成一注」，
因为任何数字串都是合法号码，读错了**没有任何办法发现**。硬约束一
（每个号码都要说得出来自哪个像素格子）针对的就是这一类票 —— 格子是它们唯一的护栏。

而两位数那几种，一注号码自己就是一道校验：`12 15 19 31 33` 必须升序、
不重复、落在 1–35 内，`05 09` 必须落在 1–12 内。OCR 读错一位，这几条基本都会崩，
解析器当场拒掉。**号码集合本身就是校验和**，再加一层格子是拿它没有的病去治它。

双色球的实测更进一步说明格子对它有害：分隔符 `-` 和两边号码只隔 0.13 个字宽，
墨迹投影只能把 `30-03` 连成一段，合并后一行 7 段正好等于 7 个号码 ——
段数对得上、内容全错，而且看起来一切正常。

**所以阶段 4 收敛成：矩阵路只服务「任意数字都合法」的那四种票
（排列3、排列5、七星彩、福彩3D）。双色球、大乐透、七乐彩、快乐8 走文本路，
力气花在基准和号码区上 —— 那一层两条路本来就共用。**

这也意味着老的文本解析路**不能删**：它不是过渡方案，是另一半彩种的正路。
要删的是"从识别结果里估几何"那条（`DigitMatrixReader`），
等四种数字型票都稳定走格子路之后再删。

## 十七、build 45 真机 + 末列改成大格

### 1. 数据：补认在干活，但末列救不回来

`35 格里认出 32 格（整块认一遍剩 8 格空的，补认补上 5 格）`

新加的那两个数一下就说清楚了：**补认本身是好的**（8 格空的补上 5 格），
补不上的那 3 格全在末列。换句话说三轮下来试过的三种办法 ——
取并集、按字宽往左让、单格补认 —— **方向都错了**。

### 2. 根因：把格子划得刚刚好，等于要求 OCR 也刚刚好

`13` 的十位是一竖，又细又淡，配准+缩放之后经常整笔掉出二值化，
于是墨迹划出来的格子只框住个位；而 Vision 在灰度图上照样看得见那一竖，
认出来的 `1` 落在格子外面，又被丢掉。往左让多少都是在赌那一笔的粗细。

### 3. 改法（用户提的）：末列切成一个**大格**

> 「因为特别号它都是在后面嘛，能不能就把它后面直接切成一个大格，
> 让它把后面识别的东西全部拼到一块？」

对。特别号右边什么都没有，那就把右边整片都算给它，认出什么就拼什么：

```
左边界 = 第 6 位右沿 和 特别号左沿 的正中间
右边界 = 特别号右沿 + 半个列距（不超过号码区右边）
```

实测这条左边界离第 6 位有 2.35 个字宽、离十位还有 0.68 个字宽的余量，
两头都碰不着。这一片里不可能出现别的号码 —— 这是版式保证的，不是赌的。

不违反硬约束一：大格照样是票面上一块说得清的像素区域，调试图上画出来就是那个框。
说不清的只是"这个数字属于哪一位"，而这一组本来就只有一位。

顺带修 `reread` 的留白：原来按格宽的 0.8 倍让，大格一乘就让到前一个号码上去了。
改成按**字高**让（`min(宽×0.8, 高×0.6)`），和格子宽度脱钩。

### 4. 大乐透退回文本路（用户定的）

版式实测确实是矩阵（第十四节），格子也划对了，但文本路本来就读得对 ——
切过去只是多一条会出错的路。`DigitTicketLayout.of(.dlt)` 改回 nil。

那组实测列位留在测试里当回归用：它是**分组挑列**最硬的一个用例
（号码矩阵中间夹着一段不是号码的墨）。

至此那条界线落地成代码：**矩阵路只服务排列3、排列5、七星彩、福彩3D**。

### 5. 复核页两处（用户提的）

- **每一注加了删除按钮。** 折痕、票底流水号、合计那一行都可能被当成一注，
  以前只能整张票删了重扫，而重扫大概率还是多认出来。和「补一注」是一对。
  删的时候 `lineModes` 要跟着删，否则逐注玩法整列错位。
- **票面合计永远显示在算出来的金额下面。** 这是整张复核页最便宜也最有用的
  一道校验：注数是识别出来的，合计是票面上白纸黑字印的，多认一注、少认一注、
  倍数看错都会让这两个数对不上。对得上也要显示，让人知道这道校验跑过了；
  没认出合计时也要说一声"这张票少了一道校验"。
  **金额本身不给改** —— 它是票面事实，对不上就去改号码和倍数。

## 十八、特别号分区（方案 A）+ 删掉坐标老路

### 1. 「几何」到底是什么（用户问的）

拿 26042 那张真票重新量了一遍（照片摆正 0.5°、605 宽裁图）：

```
①      第1位   第2位   第3位   第4位   第5位   第6位        十位  个位
76-103 150-167 214-231 279-295 343-359 407-423 470-487    556-565 575-593
```

| | 值 |
|---|---|
| 列距 | **64**（5 个间隔：64.5 / 64.5 / 64 / 64 / 63.5）|
| 字宽 | 17.5（列距 ÷ 字宽 = **3.66**，和第 3.2 节的 3.62 对得上）|
| 第6位 → 特别号个位 | 106.5 = **1.66 个列距** |
| 第6位右沿 | 487 |
| 特别号**十位**左沿 | 556 |
| **中间的空白带** | **[487, 556]，宽 69px** |

**分界线取空白带正中间 = 521.5**，换算成相对量：

> **分界线 = 第6列中心 + 0.67 × 列距**

两边各留 34.5px ≈ **2 个字宽**，对称。列距是**这张票自己量出来的**
（主矩阵六列一算就有），所以拍远拍近、裁松裁紧都跟着变，
只有 0.67 是版式常数。

还有一条帮忙的事实：**特别号取值 0–14，所以十位只可能是 `1`** ——
宽度确定（实测 9px 的细笔画），空白带的右界因此很稳。

**顺带修正文档自相矛盾的地方**：第 60–62 行一处写「列距 76」、下一行写
「号码列距 65」，测试夹具里用的是 76，这次实测是 64。1.58 那个比值是拿
103/65 算的，实测是 106.5/64 = 1.66。分界线不受影响（它取的是空白带中点，
不是偏移量的一半）。

### 2. 分区怎么做

**主矩阵回到规规矩矩的 6 列，一个特例都没有。** `trailingPitch`、
`unionRange`、`wideningTail`、`catchAllTail` 四样连同 `build` 里的两个分支
一起删掉 —— 前后三轮堆的特例，每加一层都动了收行的前提，
build 46 就是这么把整个格子路搞崩的（`挑列挑中 7 列` 之后仍然"划不齐"）。

特别号那一块按分界线切一条宽带，**认出什么就拼什么**：

```
主矩阵挑列：8 段里挑中间 6 段（① 靠字宽排除，特别号靠列距排除）
           实测得分 [0..5]=0.160  [1..6]=0.040 ✓  [2..7]=0.680
特别号：   [分界线, 号码区右沿] × 这一注的行带 → 单独认一遍
```

调试图上那一块也画成一个框，正没正、有没有咬到第 6 位，一眼可判。

### 3. 删掉「按字符坐标估几何」那条老路（用户定的）

`DigitMatrixReader` 整个删了，只把 `Row`/`Matrix`（搬去 `DigitMatrix`）和
`allDigits`（搬去 `TicketVisionScanner`）留下。

它的方向本来就是反的（认得越差、几何估得越偏），但真正的问题是
**它会盖住格子路的失败** —— 格子划不出来时它给出一个看起来差不多的答案，
于是连着几轮真机都看不出来，用户只会觉得"改了没用"。

**要说清楚的后果**：删掉之后格子路一失败，就直接掉到最老那条逐行二次识别，
结果可能更差（那条路有过"每注前面凭空多个 0"的老毛病）。
但失败会变得刺眼，而票面合计那道校验会把少认一注的票挡在导入之前。
按项目自己的原则这是对的：失败要看得见。

### 4. 顺手修一个死结：问号补不上

用户实测：七星彩的特别号识别成问号之后，**在修改弹窗里永远改不回来**。

根因在 `NumberPadSection.toggle`：特别号值域 0–14，`isPositional` 要求
上限 ≤ 9，所以它走的是号码盘不是滚轮；而 `required == 1`，
问号（`-1`）占掉了唯一的名额 ——

```swift
guard next.selected.count < required else { onReject?("已经选满 1 个") }
```

点任何一个号都被"已经选满 1 个"挡回去，而问号自己**不在号码盘上**
（−1 不在 0–14 里），也点不掉。死结。双色球的蓝球、大乐透的后区
带问号时是同一个死结。

修法：**问号占的位置不算"选满"** —— 它是"这一位还没补上"，不是一个号码。
点号的时候优先填进第一个问号的位置。`countText` 也跟着报
「已选 N，还差 M 个」，否则号码盘上一个球都没亮，却写着"已选 1"。

### 5. 问号会不会消失（用户问的）

不会，而且方向相反：

| | 现在 | 删掉老路之后 |
|---|---|---|
| 格子路成功 | 问号只出现在真的没认出的格子 | 一样 |
| 格子路失败 | 掉到坐标老路 → 还是给 5 注带 3 个问号 | 掉到逐行二次识别 → **不产问号，产「整注消失」** |

问号不是 bug，是特性。它的替代品不是"正确的号码"，是
**"错的号码，但看起来是对的"**。目标不是零问号，是零错号。
要让问号变少，唯一的办法是让格子路别失败。

## 十九、投喂次数大精简（用户驱动的重新审视）

用户的体感：**一次识别要 10 秒左右，不可接受。** 数了一遍，一张七星彩要调用
Vision **53 次**：

| 阶段 | 次数 |
|---|---|
| 预处理（找四角 + 量倾角）| 2 |
| 整票识别（彩种/期号/玩法/倍数/金额）| 1 |
| 整块号码区（原图 + 对比度）| 2 |
| 空格补认 3 格 × 6 遍 | **18** |
| **特别号 5 注 × 6 遍** | **30** |

而且后面那 48 次每次还要先做一遍 CoreImage 对比度 + 一次放大
（18 倍放大一条 186×77 的图 = 3348×1386 的位图）。

**这 48 次全是我在追七星彩那个 bug 的过程中一层层加上去的补丁**，
核心那三次（整票 1 + 号码区 2）从来就够用 —— 主矩阵 30/30 全对就是它给的。

### 1. 统一路线（两条，不再有第三条）

```
预处理（2 次）
   ↓
整票识别（1 次）→ 标签路：彩种 / 期号 / 开奖日期 / 玩法 / 倍数 / 金额
   ↓
配准（0 次）→ 号码区四角 + 左右边界
   ↓
号码路
   ├─ 格子型（排列3/5、福彩3D、七星彩）
   │    号码区整块喂一次（2 次：原图 + 对比度）→ 字符 + 坐标 → 落格子
   │    七星彩的特别号：整条窄带喂一次（1 次）→ 按行带对号入座
   │    整块漏掉的格子：每格 2 次，**封顶 6 格**
   └─ 非格子型（双色球、大乐透、七乐彩、快乐8）
        号码区整块喂一次（1 次，只挂英数模型）→ 按行拼回文本
```

### 2. 特别号：30 次 → 1 次

五个特别号在票面上本来就是一竖排、左右什么都没有。裁成**一条窄带整条喂一次**，
Vision 返回的字符带着坐标，按行带对号入座就行 —— 窄带里只有这五个数，
没有别的字符来抢坐标，比逐注裁块更准。

### 3. 拆掉那两道闸

上一版 `reread` 是「3 种放大 × 2 种对比度 = 6 遍打淘汰赛」，外加两道闸：

```swift
guard (1...2).contains(chars.count) else { continue }   // 认出 3 个字符 → 整遍扔
guard value <= maximum, chars.count > bestCount else { continue }  // 拼出超上限 → 整遍扔
```

结果是**认全了反而被丢**：`13` 只要有一遍把细竖认成 `7`、拼出 `73` 超上限，
整遍作废，于是"只认出个位"的那一遍夺冠 —— 屏幕显示 `3`，票面是 `13`，
**看起来完全正常**。这正是硬约束一要挡的那种错。

现在：两遍（原图 + 对比度）的字符**按位置取并集**，认出什么拼什么；
拼出来超上限说明认错了，报**问号**，不拿其中一位顶上。

### 4. 非格子型：一行裁一条 → 整块喂一次

`secondPass` 是一行裁一条、每条喂两遍 —— 五注的双色球就是 10 次。
它存在的理由是对的（整张照片里中文和数字混在一起，中文模型会把间距宽的
数字并掉），但**配准之后号码区本来就摆正了、只有号码、可以整块放大**，
一次调用覆盖所有注。`secondPass` 降级成配准失败时的兜底。

### 5. 新的预算

| | 现在 | 改后 |
|---|---|---|
| 七星彩 | 53 | **6～12** |
| 排列3/5、福彩3D | 21～39 | **5～11** |
| 双色球/大乐透/七乐彩/快乐8 | 13 | **4** |

### 6. 调试图现在会报 Vision 的**原文**

`特别号整条读出 5/5，Vision 给的是「13/4/9/10/2」`

前五轮都在猜「Vision 到底认出了什么」，而调试图只报得出「认出几格」。
这一条补上之后，下一轮不管哪儿出问题都是一眼的事，不用再推理。

### 7. 格子为什么不砍

用户问过：3D、排列3/5 本来就是个位数，是不是连格子都不用切？

**格子不花 Vision 调用** —— 纯像素运算（行投影 × 列投影），几毫秒。
它提供的不是识别能力，是**位置骨架**：0–9 任意数字都合法，少认一位如果
不知道位置，整注要么废掉、要么悄悄左移一位（"每注前面凭空多个 0"就是这么来的）。
有格子，少认一位就只是**一个问号落在正确的位置**。

慢的从来不是格子，是补丁。
