# 识别系统重构方案（号码识别）

> 这份文档是重构的**唯一事实来源**。所有像素测量都来自真实票面照片，
> 不是估计值。开工前先完整读一遍。

## 一、要解决什么

**标签信息（彩种、期号、开奖日期、倍数、合计）目前识别已经够用，不动它。**
问题**全部**集中在号码球：

| 症状 | 真机实例 |
|---|---|
| 整排错位 | 七星彩每注前面凭空多个 `0`，特别号整列消失 |
| 两位数丢十位 | 特别号 `13` 读成 `3`、`10` 读成 `0` |
| 无关数字被当成号码 | 排列5 把票底流水号 `00084` 读成唯一一注 |
| 裁切稍微不准就整张认不出 | 排列3 |

最危险的不是"认不出"，是**认错了还看起来对** —— `00084` 和 `3` 都是合法号码，
用户不拿票面逐位比对根本发现不了。

## 二、根因

当前流水线在**用户裁切之后直接做 OCR**，中间缺了「配准」这一步。
所有几何判据（列距、行距、边界）都只能**从识别结果里估**，
而裁切框本身是歪的、松的，估出来的东西自然跟着偏。

真正的锚点应该来自**票面自己印上去的东西**，而不是用户的裁切框。

## 三、实测数据（重要，不要重新猜）

### 3.1 体彩数字型：上下两条虚线就是基准

七星彩、排列5、排列3 的号码区被**两条长虚线**夹住，中间还包含
「玩法 / 倍数 / 合计」那一行。

检测判据（三张票实测，**零误报**）：

```
高 ≤ 6 行
横跨 > 80% 宽度
段数 ≥ 12
最长段 ≤ 5% 宽度
占空比 0.25–0.75
```

| 票 | 候选横带 | 命中虚线 |
|---|---|---|
| 七星彩 | 24 | **2** |
| 排列5 | 18 | **2**（其中一条仅 1 像素高也抓到） |
| 排列3 | 9 | **2** |

### 3.2 体彩版式比值（跟裁切、拍摄距离无关）

| | 列距 ÷ 字宽 | 行距 ÷ 字高 | 末列偏移 |
|---|---|---|---|
| 七星彩（5 注 × 7 位） | 3.62 | 1.41 | **1.58 列距** |
| 排列5（2 注 × 5 位） | 3.74 | 1.44 | 1 |
| 排列3（3 注 × 3 位） | 3.43 | — | 1 |

七星彩实测像素：字 21×29，列距 76，行距 41，
注序号列距第一列 **62.5**（和号码列距 65 几乎一样 —— 几何上分不开，
必须靠标签位置排除），特别号偏移 103。

### 3.3 福彩：没有虚线，用两行文本当基准

```
玩法:3D-单式              机号:31130622
7D92-04AE-1FB5-E411-B960/32798871/C084C   ← 上基准（哈希行）
组六: 1 8 9         (1)   ┐
组六: 0 1 7         (1)   │ 五行左边界 29-32
组三: 0 9 9         (1)   │ 右边界 328-329
单选: 5 0 6         (1)   │ 完全对齐
单选: 8 9 1         (1)   ┘
开奖期:2026091 26-04-11  合计10元   ← 下基准
```

- 哈希行格式固定：`XXXX-XXXX-XXXX-XXXX-XXXX/8位/5位`，可用正则钉死
- 这两行 Vision **每次都读得出来**（历次识别原文均在）
- `VNRecognizedTextObservation` 继承自 `VNRectangleObservation`，
  给的是**四边形**（topLeft/topRight/bottomLeft/bottomRight），自带透视信息 ——
  两行 8 个点，拟合单应绰绰有余

福彩 3D 号码区列分布（500px 宽裁图）：

| 内容 | x 范围 |
|---|---|
| `组六:` | 29–78 |
| 第1位 | 93–107 |
| 第2位 | 133–147（列距 40，字宽 15 → **2.65**） |
| 第3位 | 173–186 |
| `(1)` | 295–329（**距号码 2.7 个列距**） |

双色球：列距 51（两位数宽 36），`(3)` 距最后一个号码仅 **0.43 个列距**（很挤）。

## 四、新架构

```
                     ┌─ 体彩：虚线检测（自己算）
粗裁切 → 基准检测 ───┤
   │                 └─ 福彩：哈希行 + 开奖期行（Vision 给四边形）
   │                        ↓
   │                  TicketFrame { 号码区四角, 左边界, 右边界 }
   │                        ↓
   │                  单应配准 → 号码区摆成标准矩形
   │                        ↓
   │                  网格（列距行距成常数，不再估）
   │                        ↓
   │                  逐格识别 → 认不出标问号
   │
   └─ 标签路（整票中文 OCR）→ 彩种/期号/日期/倍数/合计   ← 完全不动
```

配准之后这些麻烦一次性消失：列距行距变常数、注序号列和倍数列在标准矩形里
是固定位置、七星彩那 1.58 个列距变成画好的格子、裁松裁歪不再有影响。

**号码区需要左右两个边界**：
- 左 = 注序号 / 玩法标签列的右侧（`①②③④⑤` / `A.B.C.` / `组六:`）
- 右 = 倍数列 `(N)` 的左侧 ← **当前代码缺这个，见下面已知 bug**

## 五、四个阶段

| 阶段 | 内容 | 验收 |
|---|---|---|
| **1** | 虚线检测 + 单应配准（排列3/5、七星彩）+ **调试可视化** | 复核页贴出配准后的号码区截图，正没正一眼看出 |
| **2** | 配准矩形里重做网格 | 七星彩五注全对，含 `13`/`10` |
| **3** | 福彩基准（哈希行 + 开奖期行），3D 先上 | 3D 五注 + 逐注玩法全对 |
| **4** | 双色球 / 大乐透**一步到位**切到新架构 | 现有用例全绿 |

**阶段 4 是用户明确决定的：不做双路裁决，直接一步到位。**
理由是长期维护和排查 bug 更清晰。旧的文本解析路在双色球/大乐透切完之后应当删除，
不留两套并行实现。

**调试可视化：常驻，设置里加开关，默认关闭。**
要画出：检测到的基准（虚线 / 两行文本）、配准后的矩形、每个格子的位置。
这样以后任何一张票出问题，用户截个图就能定位是基准没找对、格子划歪、还是单纯没认出来。

## 六、硬约束（不可违反）

1. **每一个号码都必须能说出它来自票面的哪个像素格子。**
   说得出来的才允许导入，说不出来的标问号（`NumberSet.unknown`）。
   问号未补齐**禁止导入票夹**。这样"看起来正常的错误结果"在结构上不可能出现。
2. **摆不上栅格宁可整个矩阵作废、退回上一层**，绝不允许错位。
   少认一注可以接受（用户看得见），错位不可以（用户看不见）。
3. **号码路和标签路彻底分开**，标签路一行都不要动。
4. **隐私**：全部识别在本机完成，照片不上传、不写入数据库。
   **不得引入任何云端 OCR** —— 会推翻已提交 App Store 的审核备注和隐私政策。
   端上第三方 OCR（Tesseract/PaddleOCR）也不要：它们同样按「先找文本行」工作，
   在矩阵排版上会犯一模一样的错。
5. 各彩种的配色方向不变；号码球数字保持白色。

## 七、已知的具体 bug（重构时必须一并解决）

1. **福彩 3D 的矩阵路径从来没跑起来过**：行尾 `(1)` 里的 `1` 被 tokenize 当成
   第 4 个号码，`isBetRow(columns: 3)` 因为 4 > 3 直接拒掉。号码区缺右边界。
2. **七星彩两位数特别号丢十位**（`13`→`3`、`10`→`0`），build 32/33/34 三次尝试都没修好。
3. `VNRecognizedText.boundingBox(for:)` 在 `.accurate` 下对同一个词里的**每个字符
   返回同一个框**（Apple 技术支持确认的 bug）。要逐字符坐标**必须用 `.fast`**。
4. `①` 在 Unicode 里是有数值的数字字符（`wholeNumberValue == 1`）。
   按坐标取字符时必须用 `TicketTextParser.plainDigitValue`，不能用 `digitValue`。
5. 数字型彩种值域是 0-9，**任何数字字符都是合法号码** —— 票底流水号 `00084`
   曾被读成一注。现在靠「号码必须按空白隔开」挡住，重构后要保留等价的保护。
