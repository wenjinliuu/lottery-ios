# 票面识别系统

这份文档描述**系统现在长什么样**：架构、约束、实测常量、已验证的结果、
已经证伪不要再试的路。

和隔壁 `vision-rebuild.md` 的分工：

| | 内容 | 什么时候看 |
|---|---|---|
| **本文** | 现状参考手册 | 要改这套东西之前 |
| `vision-rebuild.md` | 二十三节流水账，一轮一轮的真机反馈和推导 | 想知道**为什么**是现在这样 |

流水账里的测量数据仍然是唯一事实来源，本文只是把结论提出来。
**所有像素数都来自真实票面照片，不是估计值。要改判据，先用
`Engineering/measure.py` 量一遍真票。**

## 一、三条硬约束

这三条是整个系统的地基，任何改动都不能违反。

### 1. 每个号码都要说得出它来自票面的哪个像素

说得出来的才允许导入。说不出来的标问号（`NumberSet.unknown`，值 `-1`），
**问号未补齐禁止导入票夹**。

这条是「先有格子再去认」这个架构的来源：格子的位置由票面自己的墨迹决定，
和识别结果无关，所以每一格永远答得出"你在票面哪儿"。

### 2. 摆不上格子宁可整个矩阵作废

退回上一层，绝不允许错位。**少认一注可以接受（用户看得见），
错位不可以（用户看不见）。**

### 3. 号码路和标签路彻底分开

彩种、期号、开奖日期、倍数、合计走文本解析；号码走格子/号码区那条路。
两边不互相调用。

> **一句话总结这三条**：最大的风险不是「认不出」，是
> **「认错了还看起来对」**。`00084` 和 `3` 都是合法号码，
> 用户不拿票面逐位比对根本发现不了。

---

## 二、隐私边界（不可越过）

- **全部识别在本机完成**，照片不上传、不写入数据库。
- **不得引入任何云端 OCR** —— 会推翻已提交 App Store 的审核备注和隐私政策。
- **端上第三方 OCR（Tesseract / PaddleOCR）也不要**，理由同上。

只用 Apple Vision（`VNRecognizeTextRequest`）+ 自己写的像素运算。

## 三、整条流水线

```
拍照 / 选图
   ↓
人工框出票面                       矩形检测只给四个角的初始位置，最终由用户确认
   ↓
透视矫正 + 水平矫正                 Homography.swift / TicketImagePreprocessor.swift
   ↓
┌──────────────── 整票识别一遍 ────────────────┐
│ 只取：彩种 / 期号 / 开奖日期 / 玩法 / 倍数 / 合计金额      │
└──────────────────────────────────────────┘
   ↓
配准：找基准 → 定出号码区                TicketRegistration.swift / TicketFrame.swift
   ↓
      ┌───────────────┴───────────────┐
   格子路                          号码区整块路
（排列3/5、福彩3D、七星彩）        （双色球、大乐透、七乐彩、快乐8）
      │                                │
 墨迹投影划格子                    号码区裁出来放大 2×
 NumberGrid.swift                  一次 Vision 覆盖所有注
      │                                │
 整块认一遍 → 按坐标落格             按行带拼回原文
 空格子单独补认（封顶 6 格）              │
      └───────────────┬───────────────┘
                      ↓
              拼回整篇文本 → 解析 → 复核页
```

### 关键顺序：配准跑在识别前面

阶段 1 时配准跑在最后、只画给人看；现在它是号码那条路的**入口**。
先有几何、再去认，不是反过来。

老路（已删除）是「认出一堆字符 → 从字符坐标估几何 → 按估出来的几何摆号码」，
这条路有个死结：**认得越差，几何估得越偏；几何越偏，摆得越错。**
七星彩的特别号丢十位、排列5 把票底流水号读成一注，都是从这个死结里长出来的。

## 四、为什么分两条路

界线是**这个彩种的号码自不自带校验**：

| | 号码取值 | 自带校验 | 走哪条 |
|---|---|---|---|
| 排列3 / 排列5 / 福彩3D / 七星彩 | 0–9，任意数字都合法、可重复、无顺序 | **没有** | 格子路 |
| 双色球 / 大乐透 / 七乐彩 / 快乐8 | 两位数，升序、不重复、有值域 | **有** | 号码区整块路 |

数字型彩种读错了**没有任何办法发现** —— 格子是它们唯一的护栏。
而两位数那几种，一注号码自己就是一道校验：解析器按升序、不重复、值域一卡，
读错基本都会崩掉，再加一层格子是多余的。

### 两个反例（都试过，都退回了）

**大乐透**：版式其实**是**矩阵（`+` 独立成段、号码间距 1.36 个字宽），
真机上格子也划对了。但文本路本来就读得对，切过去只是多一条会出错的路。

**双色球**：分隔符 `-` 和两边号码只隔 **0.13 个字宽**，墨迹投影只能把 `30-03`
连成一段；合并后一行 7 段正好等于 7 个号码 —— **段数对得上、内容全错**。

## 五、关键文件

| 文件 | 职责 |
|---|---|
| `TicketVisionScanner.swift` | 总入口。整票识别、两条路的分发、把结果拼回文本 |
| `TicketRegistration.swift` | 配准：找基准、算单应、裁出摆正的号码区 |
| `TicketFrame.swift` | 号码区/票头/票尾的框，以及框↔整图的坐标换算 |
| `DashedRuleDetector.swift` | 找票面上下那两条长虚线（首选基准） |
| `InkMask.swift` | 灰度 → 大津法 → 墨迹图。**所有像素判据的地基** |
| `NumberGrid.swift` | 划格子：行投影 × 列投影 → 行带 + 列位；特别号那两列 |
| `DigitTicketLayout.swift` | 各彩种的版式表（**全是比值，没有一个像素数**） |
| `RegisteredDigitReader.swift` | 在格子里认数字、补认空格、读特别号 |
| `TicketTextParser.swift` | 文本 → 票（彩种、期号、号码、倍数、合计…） |
| `TicketScanView.swift` | 复核页 |
| `ScanDebugOverlay.swift` / `ScanDebugReport.swift` | 调试图：把格子画回票面 + 每一步的说明 |

### `InkMask` 的工作分辨率是固定的

一律先把图缩到 **1000px 宽**再量。虚线判据里「高 ≤ 6 行」是个**像素数**，
只在这个尺度上成立；直接拿 4400px 的正片去套，同一条虚线会变成二十几行高，
判据当场失效。缩图还顺带把热敏纸的颗粒噪声抹掉了。

**本文所有像素数都是在这个 1000 宽的尺度上量的。**

## 六、实测常量（不要重新猜）

### 6.1 奠基测量：Vision 在这种票上是**按竖列**读的

七星彩实测：

| | 间距 | 空白 |
|---|---|---|
| 左右相邻号码 | 76 | 55 |
| 上下相邻两注 | 41 | **12** |

**上下空隙比左右窄 4.6 倍。** 所以 Vision 的分行结果在这种票上本身就是错的，
基于它修修补补没有意义 —— 只有**每个字符的坐标**可信。

这条推出两个结论：
1. 格子路必须**整段接管**号码区，不能在 Vision 的分行上打补丁。
2. `VNRecognizeTextRequest` 必须用 `.fast`。`.accurate` 对同一个词里的每个字符
   返回**同一个** `boundingBox`（Apple 确认的 bug），拿不到逐字符坐标。

### 6.2 `merging` 的界：0.75 个字宽

「间隙不到 0.75 个字宽就是同一个号码的两位数字」。这个界不是拍的，
是把实测间隙按 ÷ 字宽 折算之后卡在**该合**和**不该合**中间：

| 该合（一个号码的两位之间） | | 不该合 | |
|---|---|---|---|
| 七星彩 `13` | 14 ÷ 21 = **0.67** | 大乐透 `①` → 第一个号码 | 11 ÷ 13 = **0.85** |
| 大乐透 `12` | 3 ÷ 13 = 0.23 | 双色球 号码之间 | 15 ÷ 18 = **0.83** |
| 双色球 | ≈ 0.15 | 大乐透 号码之间 | 17 ÷ 13 = 1.36 |
| | | 七星彩 号码之间 | 55 ÷ 21 = 2.62 |

两侧最紧的是 0.67 和 0.83，取几何中点 **0.75**，两头各留 12% 余量。

> **适用范围要跟着样本量走。** `merging` 的字宽取的是**它拿到的那几段的中位数**。
> 主号码一行有九段真数字，中位数稳；搬到只有两三段的地方（特别号那一小块），
> 混进一粒 5px 的噪点中位数就从 26 塌到 12、界从 19.5 塌到 9 ——
> build 50 就死在这儿。**那种地方要用主号码那几列的字宽，不用自己的。**

### 6.3 七星彩 26042 的完整版式（1000 宽）

| | 像素 |
|---|---|
| 五注行带 | 416–449 / 463–496 / 510–544 / 557–591 / 610–643 |
| 六位列位 | 242–269 / 331–357 / 420–445 / 509–533 / 597–621 / 685–709 |
| 字宽 / 列距 | 25 / 88 |
| **特别号十位**（只有第 1、4 注有）| 805–816，**宽 12，正好是别的数字一半** |
| **特别号个位**（每注都有）| 831–856 |
| `单式票 1倍 合计10元` 那一行 | 369–405 |
| 合计行 → 第一注的间隙 | **11 px**（行高 35）|

排列5 26088 同一处的间隙是 **57 px** —— 差五倍。
所以「合计行离号码块多近」是**版式**决定的，不是注数。

### 6.4 各彩种版式比值

| | 列距 ÷ 字宽 | 分组 | 组间距 |
|---|---|---|---|
| 七星彩 | 3.62 | 6 + 1（特别号）| 1.58 列距 |
| 排列5 | 3.74 | 5 | — |
| 排列3 / 福彩3D | 3.43 / 2.65 | 3 | — |
| 大乐透 | 1.61 | 5 + 2 | 2.34 列距，中间印 `+` |
| 双色球 | 1.42 | 6 + 1 | — |

特别号分界线：主矩阵最后一列中心右边 **0.67 个列距**。

### 6.5 拍照倾角的影响

实测 26042 是 **−0.21°**、26051 是 **+0.40°**。号码区宽约 800px 时，
把格子整行配准回票面后取四角 y 上下界，带子会被撑开 **3–6px**。
加上 Vision 文字框自带的上下留白，**11px 的间隙必然被吃完** ——
这就是「合计那一行被整行吃掉」的直接原因。

## 七、Vision 调用预算

一张票跑多少次 Vision 直接决定用户等多久。曾经一张七星彩要跑 **53 次**，
体感 10 秒，用户原话「已经是无可接受的这个时间」。

| | 精简前 | 现在 |
|---|---|---|
| 七星彩 | 53 | **6～12** |
| 排列3 / 排列5 / 福彩3D | 21～39 | **5～11** |
| 双色球 / 大乐透 / 七乐彩 / 快乐8 | 13 | **4** |

实测从 ~10 秒降到 **1～2 秒**，用户确认「速度都很快，也能接受」。

**慢的从来不是格子，是补丁。** 格子是纯像素运算（行投影 × 列投影），
几毫秒，一次 Vision 调用都不花。它提供的不是识别能力，是**位置骨架**。

省调用的三条规矩：
1. 整块认一遍，按坐标落格 —— 不要逐格去认。
2. 空格子才补认，而且**封顶 6 格**。漏得比这多说明格子没划对，再补也是白费。
3. 每格最多两遍（原图 + 加对比度），**不要搞淘汰赛**。

## 九、特别号：一个值得单独记的设计

七星彩的特别号取值 **0–14**。两位数只有 10…14，**十位必然是 1**，
而 0 不打头（票面上 `04` 就印成 `4`）。所以：

> 墨迹切出**两段** → 这一注是 1X；切出**一段** → 就是个位数本身。

**十位根本不需要被认出来**，它是从取值范围**推**出来的。
交给 Vision 的只剩一件它最擅长的事：认一个孤零零的 0–9。

这条是逼出来的。热敏票的 `1` 是一根没有衬线的竖道、宽 12px、
只有别的数字一半，孤零零摆在一片空白里 —— 连着三轮 Vision 要么只返回个位、
要么整条返回**零个字符**。而它本来就不必被认。

定位那两列的做法（build 51 定案）：

1. **个位列** = 这一块里**落墨的注数最多**的那一段（并列取最左）。
   宽度还得在 0.35–1.6 个字宽之间，免得挑中噪点或整块杂墨。
2. **必须过半的注都有墨**，否则整块作废全标问号。这一条挡的是最要命的错法：
   个位段被筛掉之后**十位列顶上来冒充个位**，屏幕上那个 `1` 看起来完全正常。
3. **十位列** = 紧挨左边、间隙不到 0.75 个字宽的那一段，字宽取**主号码那几列**的。
4. 每一注**十位上有没有墨**（≥ 个位墨量的 20%）决定 1X 还是个位数。

**这里没有宽度判据。** 一度想加「十位那一竖必须比个位窄一半」当保险，
删掉了 —— 特别号是 `11` 的时候两列一样窄，那条判据会把一注对的号判成问号。
又是「认全了反而被丢」。

## 十、三道校验

号码之外，系统还有三道交叉校验。**对没有号码校验的四个彩种，这是仅有的护栏。**

### 1. 票面合计金额

`注数 × 单价 × 倍数 × 期数` 和票面印的「合计 N 元」对不对得上。
复核页永远显示这一行：✓ 一致 / ⚠ 不一致 / ? 没认出来。

真实战果：双色球那张少一注的票，是它先报出来的（`票面合计 18 元 vs 12 元`），
比用户先发现。

**汉字要容错。** 排列3 的识别原文是 `组选单式票 1倍 台计6元` ——
`合` 被认成 `台`（就差顶上那一横）。数字那边早有 `confusion` 表
（`O→0`、`I→1`、`S→5`…），汉字这边原来一个都没有。
现在金额那条正则认 `[合台亼仓共坏总怠]\s*[计汁讣针]` + `[元兀无π]`，
**范围严格限死在这一条正则里**，前缀照旧必须 ——
票底「感谢您为公益事业贡献 2.04元」不会被误当成票面合计。

### 2. 问号（少认了）

少认了号码**不丢整注**，差几个补几个问号：

| 情况 | 说得清吗 | 做法 |
|---|---|---|
| 少认了（5 个红球，要 6 个）| ✓ 红球是无序集合，位置没有意义 | **补问号**，那一注留着 |
| 粘连（`2831`）| ✓ 已按两位拆，拆完不够走上一条 | **补问号** |
| 多认了（7 个红球）| ✗ 去重/掉头/掉尾都救不回来 | **整注丢**，但留一条警告 |

补问号有两道闸：读出来**不到一半不补**、**一个都没有不补**
（那多半根本不是号码行）。

问号那套设施是**通用的**，不分彩种：`BallView` 把任何 `value < 0` 画成
虚线问号球，`NumberPadSection` 能编辑，`hasUnknown` 扫所有区段并拦住导入。

### 3. 两遍识别打架（**当前只统计，不改结果**）

合并两遍（原图 / 加对比度）时是「第一遍赢，第二遍同位置的直接丢」。
原图读 `8`、对比度读 `3` 落在同一个框里，`3` 被**无声丢弃**。
双色球那几种有升序/不重复/值域兜着，**排列3/5、七星彩、3D 什么都兜不住**
—— 这是最后一块「认错了还看起来对」。

调试图上现在写一句「两遍识别有 N 处不一致」。**先收数据再决定**：
都是 0 → 把打架的格子标成问号是白送的保险；经常好几处 → 问号会明显变多，
得先算代价。

## 十一、调试图怎么读

复核页顶部那几句话是这套系统最重要的排障工具。**每一步都留一句，不用再猜。**

```
没凑齐两条虚线（找到 0 条），改用票面上的文字行定位
基准：机号行 + 票底出票时间行
没认出行尾的倍数 (N)，右边界空着
配准后切出 10 行、87 格
号码按配准后的格子读：5 注 × 7 位，30 格里认出 30 格
（整块认一遍剩 3 格空的，补认补上 3 格，特别号读出 5/5
 （每注 2/1/1/2/1 位，读出「13/4/9/10/2」；
  字宽 25，切出 2 段，个位 831–856，十位 805–816（间隙 15）））
```

读法：

| 看哪句 | 能定位什么 |
|---|---|
| 「找到 N 条虚线」/「基准：…」 | 配准走的哪条路 |
| 「切出 N 行、M 格」 | 墨迹切分对不对 |
| 「X 格里认出 Y 格」 | 识别率 |
| 「剩 N 格空的，补认补上 M 格」 | 补认有没有用 |
| 「每注 2/1/1/2/1 位」 | **切墨迹**的结果（几何）|
| 「读出「13/4/9/10/2」」 | **认数字**的结果（OCR）|
| 「字宽 / 切出几段 / 个位 / 十位 / 间隙」 | 特别号那两列定在哪儿 |

**把几何和 OCR 分开写**是刻意的：切出 `2/1/1/2/1` 但读出 `1?` ——
一眼就知道是个位那一格没认出来，和十位无关。

划不出格子时还会额外报：墨迹带段数 / 候选行数 / 对得齐几条 /
每行切出几段 / 定出几列 / 挑列成没成 / Vision 认出几个数字。

## 十二、已经证伪的做法（不要再试）

每一条都在真机上花过一轮 TestFlight。

| 做法 | 结果 |
|---|---|
| `VNRecognizeTextRequest` 用 `.accurate` | 同一个词里每个字符返回**同一个** boundingBox（Apple 确认的 bug），拿不到逐字符坐标 |
| 用「isolation」（带内墨 ÷ 周围墨）当虚线判据 | 七星彩的真虚线 0.36，**低于**排列5 的假对 0.45/0.41 |
| 把特别号整条竖长条一次喂 Vision | 840×1980 的竖条，Vision **返回 0 个字符** |
| 逐格 6 遍淘汰赛 + 「多数一致」「位数一致」两道闸 | **认全了反而被丢**：`13` 只要有一遍拼出 `73` 超上限，整遍作废，只认出个位的那遍夺冠 |
| 在特别号那一小块上用 `merging` 定位 | 一粒 5px 噪点把中位字宽从 26 带到 12，十位和个位合不上 |
| 按**横向**切 `compose`（只丢号码块 x 范围内的碎片）| 号码块横跨 x 140–856，而 `单式票` 86–200、`1倍` 445–497、`合计10元` 758–909 —— 三样全废 |
| 把大乐透 / 双色球切到格子路 | 见第四节两个反例 |
| 「量字形宽度反推十位」 | 前提就是错的：那个 `1` 是又粗又清晰的一道竖笔 |
| 从识别结果估几何（老路）| 认得越差几何越偏，而且会**盖住格子路的失败** —— 真正的问题连着几轮看不出来 |

   打架的格子也标成问号。
2. **七星彩偶发一格个位认不出**（26042 第 4 注的 `0`）。已经是问号，

3. **虚线检测在真票上一条都找不到**，一直在跑「机号行 + 票底出票时间行」
   这个兜底 —— 也就是说两条路其实只有一条在用。

## 十四、在这套东西上继续开发

### 铁律：先量，再改

> 之前每一次靠猜的改动都白费了，每一次先量的改动都直接定位到根因。

拿到新票照片**先用 `Engineering/measure.py` 量一遍再动代码**：

```bash
python3 Engineering/measure.py 票.jpg                  # 找虚线
python3 Engineering/measure.py 票.jpg --rows L T R B   # 量某块区域的行列
```

两个真实的例子，说明这条规矩值多少：

- build 51 排查特别号时，有两个**看起来很有道理**的猜想
  （分界线切掉了那个 `1`、两遍去重把十位吃了），量完**全被否掉** ——
  按任何一个改代码都是白烧一轮 TestFlight。
- build 52 排查合计行时，我提的第一个方案（按横向切）量完当场作废，
  而且发现它连合计本身都保不住。

### 没有 Swift 工具链

CI 是唯一的编译器。算法先**移植到 Python 验证**再写 Swift
（`grid.py` 是 `NumberGrid` 的 Python 端口，改判据时两边一起改，
拿真票和合成票跑一遍对比新旧行为）。

### 每一轮的节奏

```
量真票 → 改代码 → push main → 等 CI 绿 → 发 TestFlight → 用户看调试图 → 下一轮
```

### Swift 的两个坑

1. **长的 `+` 拼接字符串**会让类型检查器当场罢工
   （`unable to type-check this expression in reasonable time`）。
   说明文字一律用 `+=` 一句一句拼。
2. 链式的泛型/元组 `map` 同理，改成显式循环。

### 写注释的标准

这个项目的注释写**为什么**，不写**做了什么**，而且把**证伪过的路也写进去** ——
`DigitTicketLayout` 里那段「双色球为什么不走格子路」、
`NumberGrid.trailingColumns` 上那段「build 50 栽在哪儿」，都是为了
下一个人（或者下一轮的我）不要再走一遍。
